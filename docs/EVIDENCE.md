# 实测证据（阈值从哪来）

> 本文件只记录**我实际跑出来的数**。任何阈值若没有对应实验，就不该出现在 gates.js 里。
> 复现命令写在每节末尾。环境：Windows 10.0.26300 / Node v22.22.2。

## G1 · 模块像素下限 = 2px

**问题**：上游允许任意 `width`，`getScale()` 会把它折算成浮点比例；没有任何下限检查。

**实验**（29 模块 + 8 静区 = 37 单元，文本 `https://example.com/order/12345`）：

| `width` | 实际像素 | 每模块 px | jsQR | ZXing |
|---|---|---|---|---|
| 40 | 40 | 1.081 | fail | fail |
| 60 | 60 | 1.622 | pass | pass |
| 111 | 111 | 3.000 | pass | pass |
| 148 | 148 | 4.000 | pass | pass |

40px 时模块宽 1.081px：一个模块连两个像素都占不满，采样点必然落错。60px（1.62px）已能读，但处于临界。

**阈值取 2px 而非 1.62px**：这是"有实测支撑的下限"，不是"精确边界"。理由有两条——
① 1.62px 只在无噪、无模糊的理想输入下通过，任何退化都会跌破（见 G3）；
② 门限设在实测边界上会让报告在"刚好能读"和"刚好不能读"之间抖动，工程上不可用。

同时给出一条可执行的修复：`scale` 提到 ≥2 的整数（`37 × 2 = 74px`），而不是要求调用方自己算宽度。

```
node -e "const R=require('./lib/scanproof/report');R.audit('https://example.com/order/12345',{width:40}).then(r=>console.log(r.verdict,r.geometry.modulePx))"
```

## G2 · 非整数缩放导致模块宽度不均

**问题**：`Utils.getScale()` 返回浮点比例，`qrToImageData()` 用 `Math.floor((i - margin) / scale)` 反查源模块。

**实验**：PNG 中间行逐像素扫描游程长度，统计该行出现的不同宽度。

| `width` 参数 | 实际像素 | 该行游程长度集合 | 整数比例 |
|---|---|---|---|
| 132 | 132 | 29, 4, 3, 7, 17, 18, 21 | 否（3.567） |
| 133 | 133 | 29, 4, 3, 8, 18, 7, 21 | 否（3.595） |
| 148 | 148 | 32, 4, 8, 20, 24 | 是（4） |
| 264 | 264 | 58, 7, 14, 8, 35, 15, 36, 42 | 否（7.135） |
| 265 | 265 | 58, 7, 14, 8, 36, 42 | 否（7.162） |

非整数比例下，同一行内模块被量化成 3~5 种不同像素宽度，且随位置变化。

**这条闸门的诚实边界**：以上是**几何事实**（模块不等宽），但**尚未证明它单独导致解码失败**。
`width: 100` 的产物在本次所有解码器与退化场景里都能读出。因此：
- 闸门级别 = `warning`，不是 `error`；
- 报告文案写"模块宽度会漂移"，不写"扫不出来"；
- 同时给出 `width=111` 这种可直接用的取值。

`width: 100` 的另一个副作用是**静区被压**：`occlusion` 闸门实测该产物静区里 2.22% 的像素不是背景色
（模块被四舍五入挤进了留白）。这一点是像素级测量结果，不是推测。

```
node -e "const V=require('./lib/scanproof/variants');const G=require('./lib/scanproof/geometry');console.log(G.geometry('https://example.com/order/12345',{width:100}))"
```

## G3 · 退化场景阈值

每个变体阈值都调到"默认 148px 产物仍双读"与"明显过界"之间，并逐档实测过。

### 降采样

| 基础图 | ÷2 | ÷3 | ÷4 | ÷5 |
|---|---|---|---|---|
| 148px | pass | **fail** | pass | fail |
| 200px | pass | pass | pass | fail |
| 296px | pass | pass | pass | fail |

÷3 在 148px 上失败、在 200px 上通过 → 它衡量的是**绝对尺寸够不够**，不是"缩放比对不对"。
因此 `downscale-3x` 标为 `optional`（边界场景），只在报告里展示、不参与判定。
`downscale-2x` 在三种基础尺寸下都通过 → 作为必须通过的变体保留。

### 印刷噪点（盐椒）

| 噪点比例 | 双读结果 |
|---|---|
| 0.05% | pass |
| 0.1% | pass |
| 0.2% | pass |
| 0.5% | pass |
| 1.0% | pass |
| 2.0% | **fail** |

阈值取 1%（仍通过），把 2% 作为"已失效"的已知点写进文档而不是当作门限。

### 镜面高光

| 位置 / 半径 / 强度 | 双读结果 |
|---|---|
| 中心 0.22R / 0.85 | pass |
| 中心 0.34R / 1.0 | pass |
| 中心 0.50R / 1.0 | pass |
| 左上 0.25,0.25 / 0.4R / 1.0 | **fail** |

居中高光即使覆盖全图一半半径仍可读（定位图案完好）；只有盖住左上定位图案时才失效。
因此 `glare` 标为 `optional`，并注明"覆盖定位图案"这一具体位置——它不是"高光必然导致失败"的证据。

### 旋转

3° / 5° / 8° / 10° / 12° / 15° / 30° / 45° 全部双读通过（最近邻旋转，白底填充）。
`rotate-15deg` 作为必须通过的变体保留，说明"拍摄倾斜"不是主要失效原因。

### 模糊

盒式模糊 1px：通过。2px 及以上：失败（与 G1 的模块像素下限同源——模糊等效于缩小有效模块）。

### 低照度

亮度 ×0.55 + 偏移 110（模拟背光不足 + 黑位抬升）：通过。对比度仍高于 3:1 是前提。

## G4 · 双解码器的判定分歧（这是"必须两个引擎"的直接证据）

同一张图，两个解码器结论不一致的真实场景：

| 场景 | jsQR | ZXing |
|---|---|---|
| 基线 148px | pass | pass |
| 模糊 1.8（132px） | **pass** | **fail** |
| 旋转 3° | **pass** | **fail** |
| 旋转 5° | **pass** | **fail** |
| 旋转 8° | **pass** | **fail** |
| 旋转 12° | **pass** | **fail** |
| 静区被 2px 侵占（margin=4） | fail | fail |
| 降采样到 52px | fail | fail |
| 亮度 0.6 / 1.8 | pass | pass |

ZXing 在**小角度旋转**上明显弱于 jsQR（它依赖 finder pattern 的几何对齐，旋转后像素网格错位）。
若只用一个引擎，"某引擎可读"会被写成"可扫"。

因此报告结构里 `decoders.jsqr` 与 `decoders.zxing` 是**并列的两个字段**，
`consensus` 只做汇总（`read-by-both` / `read-by-one` / `no-read-by-any` / `wrong-payload` / `unavailable`），
`read-by-one` 一律降级为 `warn` 而不是 `pass`。

## G5 · 反色产物的真实行为

| 配置 | jsQR `dontInvert` | jsQR `attemptBoth` | ZXing |
|---|---|---|---|
| 深码浅底（默认） | pass | pass | pass |
| 浅码深底（`dark:#fff, light:#000`） | **fail** | **pass** | fail |

结论：反色产物**默认检测读不出**，但**不是不可扫**——扫码端开启反色检测后能读。
因此闸门是 `warning`（不是 error），报告会额外跑一次 `attemptBoth` 并把这个结果单列（`invertedRetry`），
文案明确写"多数手机原生相机支持，部分小程序/嵌入式扫码器不支持"，不替调用方下结论。

## G6 · 对比度阈值

WCAG 2.1 SC 1.4.11 要求非文本内容对比度 ≥ 3:1。实测：

| 前景 / 背景 | 对比度 | jsQR | ZXing |
|---|---|---|---|
| #000000 / #ffffff | 21.00 | pass | pass |
| #777777 / #ffffff | 4.48 | pass | pass |
| #bbbbbb / #ffffff | 1.92 | **fail** | **fail** |

1.92:1 时两个解码器都失败——与 3:1 阈值方向一致，因此取规范值而不是自己拍一个数。
注意 4.48 仍在 3:1 之上且可读，说明阈值不该设到 4.5（那是正文文本的标准，不是图形）。

## 未被验证的部分

- **真实手机摄像头**未参与。所有"可扫"结论来自软件解码器，语义是"至少一个独立解码器能读出原文"。
- **印刷网点、纸张反光、曲面贴附**等物理退化只有近似模型（盒式模糊、圆形高光），不是物理仿真。
- **低色深 / 单色屏 / 激光雕刻**等场景完全没有建模，报告里不会给出结论。
- `canvas@2` 原生模块在本机装不上，`toCanvas` / `toDataURL` 路径的产物未纳入验收（见 BASELINE.md §7）。
