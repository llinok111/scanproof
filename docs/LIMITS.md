# 能力边界（这个工具能证明什么，不能证明什么）

> 这份文件存在的理由：一个"验收工具"最大的风险不是漏报，而是**让人以为已经验过了**。
> 所以每一条能做的和不能做的都写清楚，报告的 `verdict` 必须能在读完这份文件后被正确理解。

## 1. verdict 四个档位的准确语义

| verdict | 含义 | 能推出什么 | 不能推出什么 |
|---|---|---|---|
| `pass` | 双解码器读出原文；无 error/warning 闸门；所有必须通过的退化场景也读出 | 在本次测到的条件下产物可读 | 手机一定能扫；印刷一定没问题 |
| `warn` | 能读出，但存在风险（规范允许但实证有风险 / 仅单引擎可读 / 某个退化场景失效） | 有具体风险点，报告里逐条列出 | "可以忽略" |
| `fail` | 读不出、读错、或违反规范硬性要求（静区、对比度、模块尺寸） | 这份产物不该上线 | 修不好（`suggest` 会给出已验证的修法） |
| `inconclusive` | 解码器不可用或已按要求跳过 | 未验证 | **绝不是"通过"** |

`inconclusive` 的存在是刻意的：上游测试里曾出现"5 个全 SKIP 被打印成 5/5 passed"，
本项目把"没测"和"通过"分成两个不同的值，并且退出码也不同（3 vs 0）。

## 2. 逐条闸门的能力边界

### quiet-zone（静区）
- **能测**：`margin` 参数值；以及像素级"静区内有多少像素不是背景色"。
- **不能测**：产物被放进实际页面后，周围元素（深色卡片、边框、阴影）是否侵占了静区。
  报告只看产物自身。若要把产物贴到深色底上，静区等于失效——这一点只能由使用者判断。
- **依据**：ISO/IEC 18004:2015 §6.3.8 要求 4 模块。

### module-pixels（模块像素）
- **能测**：当前每个模块占多少像素。
- **不能测**：屏幕显示尺寸、打印 DPI、观看距离。1 个模块 4px 在 27 寸屏上可能只有 0.3mm。
  要算物理尺寸，需要使用者自己乘 DPI——报告里给的是像素，不是毫米。
- **依据**：实测下限（docs/EVIDENCE.md G1），不是规范条文。

### contrast（对比度）
- **能测**：`color.dark` 与 `color.light` 的 WCAG 相对亮度比。
- **不能测**：印刷后的实际墨色、纸张底色、环境光。屏幕上的 #777 与印在灰纸上的 #777 不是一回事。
- **依据**：WCAG 2.1 SC 1.4.11 的 3:1（非文本内容），不是 4.5:1（正文文本）。

### polarity（极性）
- **能测**：深色是否比浅色更暗。
- **不能测**：目标扫码端是否支持反色检测。报告会额外跑一次 `attemptBoth` 并单列结果，
  但"某个扫码 App 不支持"这件事无法从产物推出。
- **依据**：jsQR 文档明确 `inversionAttempts` 会带来约 50% 性能开销且默认行为在变；
  实测见 docs/EVIDENCE.md G5。

### integer-scale（整数缩放）
- **能测**：缩放比例是否为整数；非整数时同一行模块被量化成几种宽度。
- **不能测**：这个漂移是否会导致失败。**实测表明 width=100（2.70px/模块）仍然可读**。
  所以它是 warning 而不是 error，文案只说"模块宽度会漂移"。
- **依据**：像素游程统计（docs/EVIDENCE.md G2）。

### occlusion（静区被压）
- **能测**：非整数缩放下模块被四舍五入挤进静区的比例（width=100 实测 2.22%）。
- **不能测**：这 2.22% 是否致命（实测仍可读）。
- **依据**：像素统计，不是推测。

### opaque-background / error-correction / module-oversize
- 三条都是 `info`，只提示不影响可扫性。`error-correction` 给的是经验建议（L 级 7% 容错在
  户外/小尺寸/加 logo 场景偏弱），不是规范强制。

## 3. 退化场景（variants）的边界

- 全部是**纯 JS、确定性、像素级**变换，不依赖 GPU/随机数 → 同一产物在任何机器上结论一致。
- **不是物理仿真**：盒式模糊 ≠ 镜头失焦，圆形高光 ≠ 真实反光，盐椒噪点 ≠ 印刷网点。
  它们只能回答"这类退化下还读不读得出"，不能回答"你的印刷厂会印成什么样"。
- **`optional` 变体不参与判定**：`downscale-3x`（衡量绝对尺寸）与 `glare`（必须盖住定位图案才失效）
  标为边界场景，只在报告表格里展示。把它们计入判定会让"默认参数"永远拿不到 pass，
  那就等于把阈值设成了"任何产物都不合格"。
- **未建模的场景**：低色深、单色屏、曲面贴附、激光雕刻、屏幕摩尔纹、动态模糊。报告对这些不给结论。

## 4. 解码器相关的边界

- 两个解码器都是**可选依赖**。装不上时报告标 `unavailable` 并让 verdict 变成 `inconclusive`，
  不会因为"少一个引擎"就把结论算成通过。
- **`@zxing/library` 锁定在 `^0.21.3`**：0.22.0 起 `engines.node >= 24`，npm 会把不满足的可选依赖
  静默跳过（不报错、不警告），于是"双解码器"悄悄变成单解码器。这个坑只在 `npm ci` 的干净环境里暴露。
  0.21.3 与 0.23.0 在 9 个代表性场景上结论一致，但**未穷举全部场景**。
- **ZXing 在 3°~12° 小角度旋转上明显弱于 jsQR**（实测，docs/EVIDENCE.md G4）。
  因此 `read-by-one` 一律降级为 `warn`：单引擎可读不等于通用可读。
- **两个引擎都不是"真机"**：手机相机有自动对焦、多帧融合、AI 增强，通常比这两个库更强；
  但某些老旧扫码枪/嵌入式模块可能更弱。报告给的是"两个独立实现的下界"，不是真机保证。

## 5. 不能从像素反推的东西（`auditBuffer` 路径）

对一张**已经生成好的图片**验收时，以下信息无法从像素恢复：

| 项 | 状态 | 说明 |
|---|---|---|
| `errorCorrectionLevel` | **unknown** | 纠错等级不体现在可见模块上（它决定数据码字分配），只能由原文参数确定 |
| `margin` 的原始设置值 | 反推（±0.5 模块） | 由四条边的留白像素中位数推断，见 `buffer.js` |
| 生成时的 `version` | 由解码器回报 | 若解码器未回报则为 `null`，此时静区模块数也无法反推 |

`auditBuffer` 的返回里有一个 `unknown` 字段专门列这些项。**不猜**。

## 6. 明确不做的事

1. **不重新实现生成器**。生成仍走上游 `lib/core`，本层只读不写（有 `compat.test.js` 逐字节锁定）。
2. **不自动改写调用方代码**。`suggest` 只给参数补丁 + 已验证的结论变化，改不改由调用方决定。
3. **不上传任何内容**。CLI 与演示页全在本地计算；演示页不发网络请求（验收脚本会检查 console 无错误）。
4. **不声称符合 ISO/IEC 18004**。本工具是"可扫性启发式验收"，不是标准一致性测试套件。
5. **不做 GS1 / Structured Append / Micro QR**。上游本身不支持（见 README 的 GS1 段落），本层不越界补。

## 7. 已知会误判的情形

| 情形 | 报告会给 | 实际 |
|---|---|---|
| 产物贴到与静区同色的底上，但容器裁掉了 1px | `fail`（静区不足） | 可能实际可读 |
| 深色品牌色 + 浅色 logo 内嵌，但 logo 在静区内 | `fail`（occlusion） | 可能实际可读 |
| 极小的 v1 码（21 模块）配 `width=64` | `warn`（3px 模块，非整数） | 通常可读，但改 `width=63` 更稳 |
| 反色产物用于支持反色的 App | `fail`（默认检测读不出） | 实际可读，报告会单列 `invertedRetry` 说明 |

这些不是 bug，是"从严判定 + 明确标注原因"的取舍：**宁可误报 fail 并给出原因，也不误报 pass**。
